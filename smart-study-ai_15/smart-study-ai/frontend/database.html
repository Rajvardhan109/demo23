Layer 3 · Data

Where every note, rating, and embedding lives.

The primary database keeps growing the way it always has — plus four new tables and a vector store that give the AI engine something to learn from.

What gets collected

Three sources of data

At registration

User data

Subject enrollment, branch, and semester — captured once, used to scope every recommendation.

Ongoing

Behavioral data

Notes viewed and downloaded, time spent per note, and ratings given — logged as the student uses the platform.

At upload

Note metadata

Subject, unit, description, upload date, and file type — the raw material the content-based model embeds.

Storage architecture
Backend API→ Feature store / vector DB↔ Primary database↔ File storage

Primary database

MongoDB as the main store, or MySQL where relational structure fits better — holds users, notes, and the four extended tables.

Feature store

Serves user interaction vectors and note embeddings at low latency, so recommendations don't wait on a full database scan.

Vector database

Pinecone or FAISS indexes note embeddings for nearest-neighbor lookup during both recommendation and NLP search.

File storage

Firebase Storage or a local server holds the actual PDF/image files — unchanged from the base system.

Tech stack
Primary DB

MongoDB (document-based, primary) or MySQL (relational, where needed).

Vector store

Pinecone (managed) or FAISS (self-hosted) for embedding search.

File storage

Firebase Storage, or a local server for on-premise deployment.

Pipeline

Scheduled jobs move fresh interaction data from user_behavior into the feature store ahead of each retrain.
